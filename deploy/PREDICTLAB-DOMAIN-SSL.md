# PredictLab: подключение predictlab.ru и HTTPS

Эта инструкция — для **существующего** сервера с Ubuntu, Nginx и установленным приложением из этого репозитория. Целевой адрес — **https://predictlab.ru**. Сертификат выпустит Certbot через Let's Encrypt после проверки владения доменом. До выполнения шагов на вашем сервере домен и HTTPS **не подключены**.

**На любом шаге при ошибке остановитесь и устраните её до продолжения.** Команды, изменяющие сервер, выполняются только вами в согласованное окно обслуживания.

**Краткий план:** резервная копия → получение новой версии → подготовка Nginx → DNS и порты → настройка URL и пересборка → выпуск сертификата → проверка продления и интеграций. Не пропускайте разделы ниже: они описывают условия и откат.

Ниже используется прямое подключение по **одному публичному IPv4** без CDN, балансировщика и IPv6. Это важно: подготовленный скрипт намеренно остановится, если DNS выбранного имени содержит AAAA-запись или A-запись не совпадает с указанным IP. Для другой схемы нужна отдельная настройка, а не обход этих проверок. HTTP-01 использует входящий порт 80; его надо оставить доступным и для последующего продления [2](https://letsencrypt.org/docs/challenge-types/).

## Перед началом

Понадобятся:

1. Доступ к панели DNS домена `predictlab.ru` и к панели VPS. Узнайте именно **публичный IPv4** VPS в панели хостинга; вывод `hostname -I` может содержать только внутренний адрес.
2. Доступ по SSH к этому серверу и права `sudo`; рабочий email для уведомлений Certbot. **Пароли, ключи SSH, `.env`, токены и полные выводы конфигурации никому не отправляйте.**
3. Окно обслуживания и проверенная резервная копия. При пересборке возможна недоступность сайта; старые платежи и webhook необходимо учесть отдельно.
4. На сервере уже работают Nginx с каталогами `/etc/nginx/sites-available` и `sites-enabled`, а приложение слушает только `127.0.0.1:3000`. Примеры предполагают каталог `/opt/Stavki_na_sport`, PostgreSQL и штатный PM2 `valuex-web` **или** Docker Compose из этого проекта. Если каталог, база, прокси или процесс отличаются — сначала уточните их, не запускайте команды вслепую.
5. Решите заранее: достаточно `predictlab.ru` или нужен также `www.predictlab.ru`. По умолчанию скрипт включает **только основное имя**. Для www надо добавить `--www` **к обоим** вызовам скрипта и настроить DNS обоих имён. HTTPS на www будет перенаправлять на адрес без www. Если www понадобится после выпуска, потребуется отдельно изменить сертификат и Nginx; повторный `prepare` существующий сайт не перезапишет.

Если `predictlab.ru` уже используется в Nginx, сертификат или одноимённый файл уже существует, либо DNS сейчас обслуживает другой сайт/почту, **остановитесь и согласуйте миграцию**. Скрипт не захватывает существующий конфиг. Он не меняет `.env`, другие сайты, firewall или базу. Настройки старого сайта в Nginx останутся, но после пересборки общее приложение и его canonical URL изменятся: старый адрес не будет полноценным отдельным магазином, и оплата со старого origin может быть отклонена.

## 1. Подключение к серверу

В Termius создайте Host: **Address** — публичный IPv4 VPS, **Port** — ваш SSH-порт (часто 22), **Username** — назначенный пользователю логин, авторизация — вашим ключом или паролем. Подключитесь. Если используете обычный терминал, замените значения в `ssh -p SSH_ПОРТ ПОЛЬЗОВАТЕЛЬ@ПУБЛИЧНЫЙ_IPV4` на свои.

Сохраните текущую SSH-сессию открытой. Ниже административные команды приведены для root:

```bash
sudo -i
cd /opt/Stavki_na_sport
pwd
```

Если `cd` не сработал, найдите **фактический** каталог проекта и используйте его вместо `/opt/Stavki_na_sport` во всей инструкции. Если Git-репозиторий или PM2 запущены не от root, команды Git, npm и PM2 выполняйте от их владельца; не меняйте рекурсивно владельца проекта и не разрешайте Git `safe.directory=*`. Для нестандартной установки лучше остановиться и уточнить процедуру.

Проверьте режим установки и работающий прокси:

```bash
systemctl is-active nginx
nginx -t
ss -ltnp | grep -E ':(22|80|443|3000|5432)\b' || true
pm2 list                         # если установлен PM2 и запущен от текущего пользователя
# ИЛИ, для Docker:
docker compose ps
```

Приложение и PostgreSQL не должны быть открыты в интернет на 3000/5432. Если вместо Nginx Apache, панель хостинга, внешний прокси, несколько серверов или внешний PostgreSQL — эта автоматическая инструкция неприменима без адаптации. Не устанавливайте второй веб-сервер поверх работающего.

## 2. Сохраните действующую версию и данные

До изменения DNS и сборки сохраните старые DNS-записи, дату и настройки у провайдера. Отдельно сохраните опубликованные редакции оферты, политики, правил и согласия с реквизитами и датой. Ребрендинг меняет текст документов; версия в коде обновлена, но она сама по себе не является архивом предыдущих текстов. До продаж покажите документы и реквизиты юристу.

На сервере:

```bash
cd /opt/Stavki_na_sport
umask 077
MIGRATION_BACKUP="/var/backups/predictlab-migration-$(date +%F-%H%M%S)"
install -d -m 700 "$MIGRATION_BACKUP" &&
  git rev-parse HEAD > "$MIGRATION_BACKUP/old-commit.txt" &&
  tar -C /etc -czf "$MIGRATION_BACKUP/nginx-before.tar.gz" nginx &&
  { if [ -f .env ]; then cp -p .env "$MIGRATION_BACKUP/root.env"; fi; } &&
  { if [ -f frontend/.env.local ]; then cp -p frontend/.env.local "$MIGRATION_BACKUP/frontend.env.local"; fi; } &&
  chmod 600 "$MIGRATION_BACKUP"/* &&
  printf 'Конфигурация сохранена в %s\n' "$MIGRATION_BACKUP"
```

Эти файлы содержат секреты. Храните копию вне сервера в защищённом месте; не добавляйте её в Git.

**Резервная копия базы обязательна.** `deploy/backup-db.sh` предназначен для штатной локальной БД этого проекта: он берёт `POSTGRES_DB`/`POSTGRES_USER` из корневого `.env`, сначала ищет контейнер `valuex_postgres`, иначе локальный PostgreSQL, и удаляет в своей папке gzip-копии старше 14 дней. Убедитесь, что это именно база, используемая работающим приложением. Если `DATABASE_URL`, роль/имя БД, контейнер или политика хранения другие, сделайте соответствующий дамп своей базы с администратором; штатный скрипт может сохранить не ту БД.

Для подтверждённой штатной установки:

```bash
cd /opt/Stavki_na_sport
bash deploy/backup-db.sh && ls -lhtr /var/backups/valuex/
```

Найдите в списке **только что созданный** `postgres_...sql.gz`, проверьте его целостность и скопируйте в защищённый каталог, введя полный путь по запросу:

```bash
read -r -p 'Полный путь к новому postgres_...sql.gz: ' DB_BACKUP
if gzip -t "$DB_BACKUP"; then
  cp -- "$DB_BACKUP" "$MIGRATION_BACKUP/database.sql.gz" &&
    chmod 600 "$MIGRATION_BACKUP/database.sql.gz" && echo 'Архив читается и скопирован'
else
  echo 'ОШИБКА: архив не читается. Остановитесь и сделайте исправную копию.'
fi
```

`gzip -t` проверяет архив, но не доказывает, что дамп правильной базы восстанавливается. Заранее проверьте восстановление в **отдельную пустую тестовую БД**, не в production. Не удаляйте старую базу, Docker volumes и `.data`.

## 3. Получите новую версию проекта

Новая версия должна быть уже отправлена в указанную ветку репозитория. Сначала убедитесь, что на сервере используется именно эта ветка и нет незакоммиченных изменений:

```bash
cd /opt/Stavki_na_sport
git branch --show-current
git status --short --branch
```

Ожидаемая ветка: `arena/e775bce3-stavki-na-sport`. Если ветка другая, есть изменения/неотслеживаемые файлы или нет доступа к репозиторию — **остановитесь** и сначала согласуйте их перенос. Не делайте `reset --hard`, не удаляйте файлы и не запускайте чистую установку `deploy/install-regru.sh` на существующей базе.

Если дерево чистое и ветка правильная:

```bash
git fetch origin arena/e775bce3-stavki-na-sport &&
  git log --oneline HEAD..origin/arena/e775bce3-stavki-na-sport &&
  git pull --ff-only origin arena/e775bce3-stavki-na-sport
```

На этом этапе новая версия кода получена, но приложение ещё надо пересобрать. Для миграции ниже **не используйте** `deploy/update-regru.sh`: он может пересоздавать/изменять роль и пароль PostgreSQL, формировать `DATABASE_URL` и перезаписывать часть env. В этой инструкции меняется только canonical URL и пересобирается уже установленное приложение.

## 4. Подготовьте Nginx до переключения DNS

Проверьте имена сайтов и убедитесь, что `predictlab.ru` ещё не занят. Вывод полного `nginx -T` может содержать конфиденциальные параметры — не публикуйте его.

```bash
nginx -T 2>&1 | grep -Ei 'server_name|listen|predictlab\.ru' || true
for tool in nginx certbot dig curl; do command -v "$tool" || echo "НЕТ: $tool"; done
```

Nginx уже должен быть установлен и запущен. Если на Ubuntu отсутствуют `certbot`, `dig` или `curl`, установите **только недостающие** пакеты через `apt`: `certbot`, `dnsutils`, `curl` соответственно. Например, для всех трёх отсутствующих:

```bash
apt-get update && apt-get install -y certbot dnsutils curl
```

Если Certbot уже установлен другим способом, не ставьте вторую копию поверх него. Перед установкой пакетов и перезагрузкой Nginx резервная копия из шага 2 обязательна.

Из корня проекта выполните **один** вариант:

```bash
# Только predictlab.ru:
bash deploy/setup-domain-ssl.sh prepare predictlab.ru

# ИЛИ, если www тоже нужен (не выполняйте оба варианта):
# bash deploy/setup-domain-ssl.sh prepare predictlab.ru --www
```

Скрипт создаёт отдельный `/etc/nginx/sites-available/predictlab.ru.conf`, не перезаписывает старые сайты, проверяет `nginx -t` и локальный путь проверки сертификата. Пока сертификата нет, новый HTTP-сайт отдаёт **503**, кроме `/.well-known/acme-challenge/`; пароли и данные по HTTP вводить нельзя. Если проверка завершилась ошибкой, прочитайте её, проверьте `nginx -t` и состояние сервиса; не удаляйте чужие файлы. При стандартной ошибке подготовки скрипт пытается удалить только созданный им конфиг и вернуть прежнюю конфигурацию.

## 5. Настройте DNS

Сначала определите, где реально размещена DNS-зона: регистрация домена в REG.RU не означает, что его DNS-серверы тоже управляются там. `dig +short NS predictlab.ru` поможет увидеть делегированные NS. Откройте **управление DNS-записями у действующего DNS-провайдера**. В REG.RU названия экранов зависят от типа панели; пример управления записями приведён в справке [1](https://help.reg.ru/support/dns-servery-i-nastroyka-zony/nastroyka-resursnykh-zapisey-na-hostinge).

Добавьте или измените запись:

| Тип | Имя / поддомен | Значение |
|---|---|---|
| A | `@` (или пустое поле/`predictlab.ru` — зависит от панели) | **ваш публичный IPv4 сервера** |
| A или CNAME, только если выбран www | `www` | тот же IPv4 **или** CNAME на `predictlab.ru.` |

Не должно остаться других A-адресов выбранных имён или AAAA-адресов: скрипт рассчитан на один IPv4. Если www не выбран, он не настраивается и может продолжить вести на прежний адрес — проверьте его отдельно. Строка CNAME на `www` допустима, но вместе с CNAME для того же имени нельзя оставлять другие конфликтующие записи. Если старые A/AAAA используются другим сервисом, не удаляйте их без плана миграции. **Не удаляйте MX, почтовые TXT, DKIM, NS и другие несвязанные записи.** Сохраните старые значения для отката.

Дождитесь распространения и проверьте не только локальный DNS сервера, но и публичный резолвер; при необходимости проверьте с другого устройства/провайдера. Пример:

```bash
dig @1.1.1.1 +short A predictlab.ru
dig @1.1.1.1 +short AAAA predictlab.ru
# Только если вы выбрали www:
dig @1.1.1.1 +short A www.predictlab.ru
dig @1.1.1.1 +short AAAA www.predictlab.ru
```

В A-ответах все IPv4 должны совпадать с публичным IPv4 сервера. В AAAA-ответах не должно быть IPv6-адресов; при CNAME может дополнительно выводиться имя с точкой на конце. Если публичные резолверы недоступны с VPS, проверьте эти записи через другое надёжное устройство/инструмент. Разные кеши могут обновиться не одновременно; не начинайте выпуск, пока ответы расходятся.

Проверьте также ограничения CAA и состояние DNSSEC, особенно если ранее использовался другой центр сертификации:

```bash
dig @1.1.1.1 +short CAA predictlab.ru
dig @1.1.1.1 +short CAA www.predictlab.ru   # если используется www
dig @1.1.1.1 +short CAA ru
dig @1.1.1.1 predictlab.ru A +dnssec | grep -E 'status:|flags:'
```

Отсутствие CAA обычно не ограничивает выпуск; при существующей ограничивающей записи должна быть разрешена `letsencrypt.org` и метод HTTP-01, с учётом наследования записей [1](https://letsencrypt.org/docs/caa/). `SERVFAIL` может указывать на проблему DNSSEC. Не меняйте CAA или DS-записи наугад: сначала уточните их назначение у администратора DNS.

## 6. Проверьте firewall и порты

На VPS и в сетевом экране панели хостинга разрешите входящие TCP **80 и 443** к этому серверу. Порт 80 нужен для HTTP-01 и будущего продления, 443 — для HTTPS. Сохраните существующий доступ по SSH на **вашем** порту; исходящие DNS и HTTPS тоже должны работать. Если UFW уже используется, сначала изучите его правила:

```bash
ufw status verbose
# Только если UFW активен и политика сервера допускает эти правила:
ufw allow 80/tcp
ufw allow 443/tcp
```

Не выполняйте `ufw enable`, `ufw reset` и не удаляйте правила SSH без отдельной проверки: можно потерять доступ. Если перед VPS есть firewall провайдера, настройки UFW его не заменяют.

## 7. Задайте canonical URL и пересоберите приложение

Предупредите пользователей и на время работ остановите новые продажи, особенно если есть ожидающие платежи. Не меняйте секреты, учётные записи и параметры базы. Старые платежи могут ещё возвращать клиента или уведомление на прежний адрес; не отключайте его до сверки заказов и завершения переноса интеграций.

В корневом `/opt/Stavki_na_sport/.env` найдите строку `NEXT_PUBLIC_SITE_URL=` и установите **ровно одно** значение:

```dotenv
NEXT_PUBLIC_SITE_URL=https://predictlab.ru
```

Редактируйте файл, например `nano /opt/Stavki_na_sport/.env`: сохранить — Ctrl+O, Enter, выйти — Ctrl+X. **Не копируйте `.env.example` поверх действующего `.env` и не меняйте другие строки.** Для PM2 также измените ту же строку в действующем `frontend/.env.local`; если используемые файлы или переменные окружения отличаются, уточните активную конфигурацию. Убедитесь, что в каждом редактируемом файле нет второй такой строки:

```bash
grep -n '^NEXT_PUBLIC_SITE_URL=' /opt/Stavki_na_sport/.env
# Только для PM2:
grep -n '^NEXT_PUBLIC_SITE_URL=' /opt/Stavki_na_sport/frontend/.env.local
```

Пересборка обязательна: Next.js встраивает публичный адрес при сборке. Выберите **один** используемый режим. Примеры применимы к штатной установке; при внешней БД, нестандартном Compose или другом пользователе процесса сначала адаптируйте их.

### Вариант A: PM2

Запускайте npm и PM2 от владельца процесса. Во время пересборки сайт будет недоступен. Нужна совместимая версия Node.js (для этой версии Next.js — не ниже 20.9; штатный Docker использует Node 22).

```bash
cd /opt/Stavki_na_sport/frontend &&
  node -v &&
  pm2 describe valuex-web &&
  pm2 stop valuex-web &&
  npm ci --no-audit --no-fund &&
  NEXT_PUBLIC_SITE_URL=https://predictlab.ru NODE_OPTIONS='--max-old-space-size=1536' npm run build &&
  NEXT_PUBLIC_SITE_URL=https://predictlab.ru pm2 restart valuex-web --update-env &&
  pm2 save &&
  cd /opt/Stavki_na_sport
```

Если сборка или перезапуск завершились ошибкой, не продолжайте к выпуску сертификата. Проверьте `pm2 logs valuex-web --lines 100 --nostream`; при необходимости используйте план отката ниже. Не создавайте новый процесс с пустой конфигурацией.

### Вариант B: Docker Compose

Для штатного Compose с контейнерами `valuex_web` и `valuex_postgres`:

```bash
cd /opt/Stavki_na_sport &&
  docker compose ps &&
  NEXT_PUBLIC_SITE_URL=https://predictlab.ru docker compose build web &&
  NEXT_PUBLIC_SITE_URL=https://predictlab.ru docker compose up -d --no-deps web
```

Команды пересобирают и заменяют веб-контейнер, не пересоздавая PostgreSQL намеренно. Возможен короткий перерыв. Не выполняйте `docker compose down -v`, `docker volume rm`, очистку volumes или установку с нуля. Если сервер использует другой Compose-файл/проект или внешнюю БД, сначала проверьте его реальные параметры.

В обоих режимах проверьте приложение **до** выпуска сертификата:

```bash
curl -i http://127.0.0.1:3000/api/health
```

Ожидается HTTP 200, `status: "ok"`, рабочий PostgreSQL и настроенные флаги безопасности. HTTP 503 означает, что требуется исправить проблему хранилища или секретов; не удаляйте `DATABASE_URL` для обхода. Этот локальный запрос не подтверждает DNS, TLS или внешние интеграции.

## 8. Выпустите сертификат и включите HTTPS

В той же SSH-сессии подставьте **реальные** значения между кавычками. Ниже — не реальные IP и email:

```bash
SERVER_IP='ВСТАВЬТЕ_ПУБЛИЧНЫЙ_IPV4_СЕРВЕРА'
CERT_EMAIL='ВСТАВЬТЕ_EMAIL_ДЛЯ_CERTBOT'
cd /opt/Stavki_na_sport

# Только основное имя, если prepare был без --www:
bash deploy/setup-domain-ssl.sh issue predictlab.ru "$CERT_EMAIL" "$SERVER_IP"

# ИЛИ, если prepare был с --www (не выполняйте оба варианта):
# bash deploy/setup-domain-ssl.sh issue predictlab.ru "$CERT_EMAIL" "$SERVER_IP" --www
```

Выбор `--www` должен совпадать с шагом 4. Скрипт повторно проверит локальный DNS, безопасную временную конфигурацию и health приложения; Certbot через webroot проверит домен извне, затем новый конфиг будет переключён на HTTPS. HTTP и выбранный www перенаправляются на `https://predictlab.ru` с сохранением пути и параметров. Старые конфиги Nginx скрипт не переписывает. Путь проверки ACME остаётся доступным по HTTP для продления.

Если Certbot не прошёл DNS/CAA/HTTP-проверку и сертификат **не создан**, временная заглушка остаётся: устраните причину и повторите тот же `issue`. При любой ошибке сначала посмотрите `certbot certificates` и `/var/log/letsencrypt/letsencrypt.log`. Если сертификат уже появился, а конфиг не переключился, **не запускайте выпуск повторно вслепую**: скрипт не перезаписывает существующий сертификат; сохраните диагностику и попросите администратора завершить настройку с этим сертификатом. Аналогично, если HTTPS-конфиг сохранён, но финальный healthcheck не прошёл, проверяйте приложение и Nginx, не выпускайте новый сертификат.

## 9. Проверьте сайт и автоматическое продление

Проверьте с сервера **и отдельно с телефона/компьютера вне VPS**:

```bash
curl -I http://predictlab.ru/
curl -I https://predictlab.ru/
curl -fsS https://predictlab.ru/api/health
curl -fsS https://predictlab.ru/robots.txt
curl -fsS https://predictlab.ru/sitemap.xml | head -c 1000
# Только если выбран www:
curl -I http://www.predictlab.ru/
curl -I https://www.predictlab.ru/
```

HTTP и HTTPS на www должны вести на `https://predictlab.ru/`, основной HTTPS должен открываться без предупреждений сертификата; health — HTTP 200. В `robots.txt` и sitemap должны использоваться адреса `https://predictlab.ru`. Не вводите логин/пароль до проверки значка замка и правильного домена. Посмотрите срок и имена сертификата:

```bash
certbot certificates
openssl s_client -connect predictlab.ru:443 -servername predictlab.ru </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

Скрипт создаёт исполняемый hook `/etc/letsencrypt/renewal-hooks/deploy/predictlab.ru-reload-nginx`: после успешного продления именно этого сертификата он проверяет конфиг и перезагружает Nginx. **Создание hook не означает, что планировщик уже работает.** Проверьте таймер/cron вашей установки Certbot:

```bash
systemctl list-timers --all | grep -i certbot || true
systemctl status certbot.timer --no-pager || true
ls -l /etc/letsencrypt/renewal-hooks/deploy/
```

Для пакета Ubuntu, если `certbot.timer` существует, но отключён, включите его: `systemctl enable --now certbot.timer`. Если Certbot установлен через snap или использует cron, найдите и проверьте **его** штатное расписание, не создавая второе наугад.

Перед dry-run просмотрите существующие pre/post/deploy hooks: они могут выполнять действия и для других сервисов. Затем проверьте продление **только этого сертификата**:

```bash
certbot renew --dry-run --cert-name predictlab.ru
# Отдельная проверка созданного hook: выполняет nginx -t и reload Nginx.
RENEWED_LINEAGE=/etc/letsencrypt/live/predictlab.ru /etc/letsencrypt/renewal-hooks/deploy/predictlab.ru-reload-nginx
```

На версиях Certbot, поддерживающих `--run-deploy-hooks`, можно дополнительно выполнить `certbot renew --dry-run --cert-name predictlab.ru --run-deploy-hooks` после проверки других hooks. В обычном dry-run deploy-hook не запускается. Успешный dry-run не доказывает работу таймера; проверяйте расписание, журнал Certbot и подаваемый сайтом сертификат. Ошибка hook может не отражаться в итоговом коде возврата Certbot [1](https://eff-certbot.readthedocs.io/en/stable/using.html). Не делайте частые принудительные выпуски: у центра сертификации есть лимиты.

## 10. Проверьте название, интеграции и пользователей

1. Откройте `https://predictlab.ru`, `/login` и `/admin`. Точное старое значение бренда `VALUEX` отображается как **PredictLab**; при следующей обычной записи оно сохраняется в новом виде. Другие ранее заданные названия не перезаписываются: при необходимости задайте `PredictLab` в админке → «Настройки» → название проекта и сохраните. Пользователи, заказы, пароли, реферальные коды и внутренние имена БД/куки не переименовываются.
2. На новом домене браузерные cookies и согласия отдельные: существующим пользователям нужно войти заново теми же данными. Telegram Web/Mini App может иметь отдельную сессию. Старые реферальные коды сохраняются, но старые URL продолжат работать только пока доступен старый домен и настроено сохранение пути/параметров.
3. Проверьте в админке реальные ссылки на поддержку и Telegram-канал, контактную почту и реквизиты. Старые ссылки сохранены, чтобы не подменять чужие аккаунты; обновите их вручную на ваши действительные адреса. Убедитесь, что документы и версия согласий соответствуют опубликованной редакции.
4. В личном кабинете ЮKassa замените URL уведомлений на **`https://predictlab.ru/api/v1/webhooks/yookassa`**, настройте нужные события и сохраните. Сверьте ожидающие платежи и проверяйте доставку уведомлений в кабинете ЮKassa и заказы в админке. Не считайте редирект старого webhook заменой настройки провайдера; неизвестный результат платежа сначала сверяется, а не оплачивается повторно.
5. Войдите на **новом HTTPS-домене** в админку → «Настройки», сохраните корректные настройки бота и нажмите «Установить кнопку Mini App». Приложение устанавливает Mini App **`https://predictlab.ru/tg-app`** и защищённый webhook **`https://predictlab.ru/api/v1/webhooks/telegram`**. Проверьте результат в Telegram. Старые привязки, созданные до обновления безопасности, нужно переподключить. При неизвестном результате отправки сначала проверьте канал, прежде чем повторять.
6. Проверьте поисковые панели и Яндекс.Метрику, новые sitemap и ссылки в рекламе/соцсетях. После проверки HTTPS и интеграций отдельно спланируйте перенаправление старого домена с сохранением пути и query-параметров. Старому HTTPS-имени при этом по-прежнему нужен действующий сертификат. Не перенаправляйте или не выключайте старые webhook/return URL, пока есть зависящие от них операции; провайдеры могут не следовать редиректам.
7. Проверьте безопасную тестовую покупку **только в отдельном тестовом окружении и базе**. `TEST_INSTANT` выдаёт доступ без реальных денег; не переключайте работающую кассу в демо для проверки. Реальную кассу и уведомления проверяйте по согласованной процедуре провайдера.

## Откат и диагностика

- **Откат DNS:** верните сохранённые значения в той же DNS-зоне и дождитесь распространения. Пока записи указывают на этот VPS, не оставляйте новый HTTP-домен без защиты: после удаления его vhost запросы могут попасть в старый default-сайт. Не удаляйте почтовые записи.
- **Откат приложения:** приостановите продажи и зафиксируйте ожидающие операции. Верните только предыдущее значение `NEXT_PUBLIC_SITE_URL` в активных env-файлах, пересоберите и перезапустите тот же режим по шагу 7, обновите webhook/кнопку Telegram обратно и проверьте старый HTTPS. Восстановление старой версии кода планируйте отдельно по записанному коммиту. Не восстанавливайте старый `.env` целиком поверх изменившихся секретов и БД.
- **Данные:** не откатывайте базу к старому дампу автоматически — можно потерять новые заказы и платежи. Перед любым восстановлением сделайте свежую копию и проведите сверку с ЮKassa; сначала проверяйте восстановление отдельно.
- **Новый Nginx-конфиг:** если нужно отключить его, сначала вручную убедитесь, что `/etc/nginx/sites-enabled/predictlab.ru.conf` — ссылка на созданный этим скриптом файл, а первая строка `sites-available/predictlab.ru.conf` начинается с `# Managed by setup-domain-ssl.sh`. Только тогда можно удалить **эту ссылку**, не другие сайты, выполнить `nginx -t` и `systemctl reload nginx`. При ошибке верните ссылку и восстановите рабочую конфигурацию; архив из шага 2 предназначен для ручного восстановления с проверкой. Не удаляйте сертификаты, которые ещё могут обслуживать трафик.
- **Сертификат не выпускается:** проверьте публичные A/AAAA и CAA, DNSSEC, доступность TCP 80 извне, `nginx -t`, `/var/log/letsencrypt/letsencrypt.log` и свободное место. Не используйте `curl -k` как доказательство корректного TLS и не обходите проверку IPv6/IP скрипта.
- **502/503:** `systemctl status nginx`, `nginx -t`, локальный `/api/health`, затем `pm2 logs valuex-web --lines 100 --nostream` **или** `docker compose logs --tail=100 web`. Не публикуйте логи без проверки на секреты. Если БД недоступна, приложение не переключается на локальный JSON; устраните проблему подключения к сохранённой БД.
- **Сертификат на диске и в браузере отличается:** после проверки hook и `nginx -t` проверьте перезагрузку Nginx, затем сравните отпечатки:

```bash
openssl x509 -in /etc/letsencrypt/live/predictlab.ru/fullchain.pem -noout -fingerprint -sha256 -dates
openssl s_client -connect predictlab.ru:443 -servername predictlab.ru </dev/null 2>/dev/null | openssl x509 -noout -fingerprint -sha256 -dates
```

Ни одна из команд этой инструкции не была выполнена на вашем production-сервере автоматически. Для реального подключения нужны ваши доступы, значения IP/email и проверки на месте.
